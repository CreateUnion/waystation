# waystation 架构说明

本文面向希望理解 waystation 实现原理的开发者，内容只取自各模块头部的代码注释与 `README.md`
中已有的事实，不引入实现之外的设计意图。用户可见行为、配置项与安全披露以 `README.md` 为准；
当前包版本以 `package.json` 为准。

## 1. 分层概览

### 1.1 三个运行角色

| 角色 | 粒度 | 职责 | 组合根 |
| --- | --- | --- | --- |
| **核心**（core） | 每个数据根一个单例 Node 进程 | 数据、网络、定时器与工具执行的唯一持有者与唯一写者；持有工具注册表与执行上下文；不持有会话凭据（注入口写入端在桥） | `src/core/main.js` |
| **桥**（bridge） | 每个 Claude Code 会话一个 MCP stdio 子进程 | MCP 门面与工具目录、调用转发、本会话注入口写入、核心不可达时的 `ws_status` 差错合成 | `src/bridge/main.js` |
| **会话席位**（seat） | 一个会话在一个协作中的参与身份，键为 `(instanceId, sessionId)` | 在席、可见性与投递的最小记账单位；站长本身也是一个席位 | `src/collab/local.js` 等 |

核心与桥的分工是「纯转发件」原则：桥不认识协作、不认识网络、不认识数据，只读
`run/core.json` 以建立连接；除 `ws_status` 在核心不可达时的差错载荷外，桥不解析业务内容。
工具面共 **28 项**，规格的单一权威在 `src/tools/specs.js`；工具目录在桥侧独立可用——核心未启动时
`tools/list` 照常应答，调用才等待核心。

机器只是载体：LAN 端点、寻址与传输仍按实例（`instanceId`），而**在席与可见性一律按会话席位记账**。
同一台机器上的多个会话共享一个核心与一个身份，但各自成席、各自收件、各自静音；机器不占席位、不批准。
两个监听面分别服务于不同范围：本机 IPC（命名管道／Unix 套接字，以及 TCP 环回）与局域网 TCP
（锚点端口 7321，槽位段 7321–7328）。

### 1.2 一次工具调用的路径

1. MCP 客户端经 stdio 调用桥；
2. 桥的转发 registry 先 `ensureCore()`（必要时探测并冷启核心），再把调用编码为 IPC `call` 帧；
3. 核心侧的注入路由执行 adopt 判定（写类调用是否可夺席／是否有本机席位）、工具 handler、
   写点记账与 notice 附加，并保证**每次 `call` 必回恰一帧 `result`**（含超时与异常路径）；
4. 桥按 `id` 收口在途调用，把结果原样交回 MCP 客户端。

注入方向则相反：核心渲染消息文本（桥不渲染不解析），经 IPC `push` 帧送到目标会话的桥；
桥把文本写入本会话的注入口后回 `delivered` 回执。核心等待回执的上限为 2 秒，超时按未注入处置。

### 1.3 数据布局

默认数据根为 `~/.waystation/`（`WAYSTATION_HOME` 可覆盖；显式数据根必须显式配置端口）。

| 路径 | 内容 |
| --- | --- |
| `config.json` | 身份名、端口、投递与席位参数、确认门默认值、`dispatch.*` 与 `retention.*` 等 |
| `run/core.json` | 运行描述符：pid、端点、token、状态、心跳、启动截止期等（独占创建，兼作核心锁） |
| `run/core-stop.json` | 核心退出时的本机席位快照，供重启对账 |
| `collabs/<collabId>/` | 每协作目录：`carrier.json`、`ledger.jsonl`、`snapshot.json`、`member.json`、`seats/<sessionId>.json`、`invites.json`、`pending-invites.json`、`outbox.jsonl`、`inbox.jsonl`、`handover-offers.json`、`departed.jsonl`、`recovery.json` 等 |
| `sessions/<sessionId>.json` | 会话级状态栏指示文件（由核心写；桥断开即删） |
| `known-hosts.json` | 发现辅助：见过的「地址:端口」、实例标识、能力证据与会话短码 |
| `dispatch-rules.md` | 调度纪律——调度（dispatch）全员纪律的单一权威源（收编通知实时读取） |
| `dispatch/state.json` | 调度编排状态（组员 / 任务表 / 调度长心跳；`dispatch.state_path` 可改位置；`dispatch.persist=false` 时不产生） |
| `archive/collabs/` | 保留期清理的已结束协作归档（gzip 清单；受同一 `collabs_days` 窗口约束） |
| `logs/` | 核心的文件日志（桥不写文件日志，诊断走 stderr） |

### 1.4 工具面错误响应

工具失败统一返回 `isError` ＋ JSON 错误对象：

```json
{ "ok": false, "code": "kebab-case-code", "message": "人话描述", "hint": "修复建议" }
```

- **成功路径不受影响**：成功返回保持各工具原有结构；错误对象保留 `ok` / `message`，旧调用方按原字段读取仍成立。
- **code 是稳定契约**：调用方按 `code` 分支，不匹配 `message` 文案；新增 code 必须在 `src/util/errors.js` 的 `ERROR_HINTS` 配一句可执行建议（可被具体调用点覆盖）。
- **单一权威**：工具层（`tools/*`）、协作服务（`collab/dispatch.js`）、核心路由兜底与桥侧核心不可达差错共用 `src/util/errors.js`——桥与核心的错误载荷因此同构。
- **桥侧 `ws_status` 例外**：核心不可达时仍合成 `core:{available:false, reason}` 与 `bridge:{version, app}`，并**同时**带统一错误四字段；这仍是「桥是纯转发件」原则的唯一登记例外。
- **dispatch 子结果**：`ws_dispatch_claim` 顶层成功，逐目标 `status:'rejected'` 条目带 `code` / `reason` / `hint`（保留 `reason` 兼容），便于调度长按稳定 code 识别 `session-not-visible` / `bridge-stale` / `claim-rejected`。

### 1.5 状态视图与资源面

`ws_status` 有 `compact`（缺省）与 `full` 两种视图：

- **compact**：只保留首检与调度长提示词真正依赖的字段——`ok`、`version`、`name`、`identityName`、`instanceId`、`pid`、`startedAt`、`core:{pid, app, endpoint}`、`site`、`net:{available, reason}`、`host.resources`、完整 `dispatch` 段、协作计数摘要 `collab:{collabs, active, completed, terminated}`，并附 `viewHint` 指向 full。
- **full**：与 0.2.6 既有输出逐字段一致（路径、端口、节点版本、`net` 全量计数器、`collab` 全量计数与 `identityHint` 均保留），仅新增 `host.resources`；不新增 `viewHint`。
- **不变式**：任何视图都保留 `ok`、`version`、`dispatch`（无调度时为 `null`，字段不消失）与 `dispatch.slaves`（有调度时为数组）；非法 `view` 返回统一错误 `invalid-view`。
- **`host.resources`**：`{ freeMemMB, totalMemMB, claudeProcs, nodeProcs }`。内存取 `node:os` 的 `freemem`/`totalmem`；进程数按平台读系统进程清单（Windows `tasklist` / POSIX `ps`），短时缓存、探测失败计零，不阻断工具主链，也不作为资源裁决依据。

`config.dispatch.resource_guard`（`enabled` 默认 true、`min_free_mem_mb` 默认 2048 / 范围 256–65536、`max_slaves` 默认 8 / 范围 1–64）只驱动 `ws_dispatch_claim` 返回的 `warnings`：空闲内存严格小于阈值、或当前组员数达到上限时，附实测数字与释放建议；**只警告不拒绝**，不改收编结果。非法配置值在加载时逐项回落默认并各告警一次，未知子键保留。

## 2. 进程与通信

### 2.1 本机 IPC

**端点。** Windows 为命名管道 `\\.\pipe\waystation-<rootDigest>`；POSIX 为
`<数据根>/run/core.sock`。`rootDigest` 复用同一摘要函数，多数据根天然隔离。
从 0.2.5 起核心**并行监听 TCP 环回 `127.0.0.1` 的 ephemeral 端口**，供跨 Session 拨入
（服务上下文冷启的核心不受命名管道 ACL 的跨 Session 限制）；端点写入 `run/core.json` 的
`ipc.tcp` 字段，与旧端点双监听，保证新旧桥混配可用。TCP 只绑显式 IPv4 环回，桥侧也拒绝
描述符里任何非 `127.0.0.1` 的 TCP 端点。

**帧协议。** IPC 为 NDJSON（一行一帧 JSON），帧协议版本 `ipcV` 只在帧契约真变时人工递增。
单帧上限 1 MiB，标识与短文本字段按 512 字节计。帧类型共 12 种：`hello`、`welcome`、`call`、
`result`、`push`、`delivered`、`replace`、`core-restarting`、`register-update`、`ping`、`pong`、`bye`；
每端只接受自己方向入站的类型，未知类型与方向不符一律拒帧计数（连接保持）。
入站帧使用前都过逐字段校验；额外字段忽略（前向兼容）。

**认证。** 桥连接后的首帧必须是 `hello`，携带核心每次启动轮换的 token（64 位十六进制，
存于 `run/core.json`）。认证阶段的所有失败共用同一条固定回执（错 token、缺 token 与形态失败
不可区分）；版本不兼容则由 `welcome{ok:false, code:'version'}` 携带核心自身的 `ipcV` 作为换代方向判据。
POSIX 下 `run/` 以 0700 创建、套接字文件 0600；无法保证 0700 时如实告警——token 的保密性由
`run/` 权限承重。信任边界（本机同用户进程视为可信）见第 7 节指向的 README 章节。

**心跳。** 默认 10 秒一次 `ping`/`pong`；30 秒内没有收到任何帧即判定对端卡死并断开。
连接与握手另有 5 秒／10 秒期限。桥侧另有**常驻心跳监督**：默认每 10 秒主动探测一次
（`WAYSTATION_BRIDGE_HEARTBEAT=<毫秒>` 可调，`=0` 关闭；单次等待默认 30 秒）——
已注册态发 `ping` 等任一入站帧，超时即强制断开并进入重生流；未注册态每拍调用既有
`ensureCore`（四态判定／冷启／换代窗口全部复用），使恢复不再依赖 60 秒慢速重试窗口。
心跳关闭或连接件不支持时，原有断连收口与重试计时器照常工作。

**运行描述符与状态。** `run/core.json` 以「独占创建」取得，同时是核心锁、运行描述符与凭据三合一；
取得后的写入使用原子替换。状态取值为 `starting`、`waiting`、`ready`；心跳周期刷新，运行期写盘失败只告警、
绝不因写盘问题退出进程。描述符包含 `v`、`ipcV`、`appVersion`、`pid`、`endpoint`、`ipc.tcp`、`token`、
`identity`、`port`、`startedAt`、`status`、`statusDetail`、`startupDeadline`、`heartbeatAt`、`startupError` 等字段。

### 2.2 传输选择与回滚

桥连接核心时按环境变量 `WAYSTATION_IPC_TRANSPORT` 选择端点：

| 取值 | 行为 |
| --- | --- |
| `auto`（缺省） | 优先使用 `core.json` 的 TCP 环回端点；失败回退旧端点一次（认证类失败也回退，token 仍由 `hello` 校验） |
| `pipe` | 强制旧端点（命名管道／Unix 套接字），用于整体回滚 |
| `tcp` | 只使用描述符里的 TCP 端点；描述符没有合法 TCP 端点时仍回退旧端点 |

非法取值按 `auto` 处理。TCP 拨入失败会回退旧端点，并计数 `transportFallbacks`。

### 2.3 局域网面

核心的 LAN 面由四个组件组成，通过装配层解除循环依赖：

- **发现（UDP）**：会话期间在全部网卡监听，按接口计算广播地址逐卡收发；扫描 =「每个广播地址 ×
  槽位段逐端口」的探测 + 已知主机清单单播兜底。默认端口锚点为 **7321**，槽位段为
  **7321–7328**（8 个槽位）；锚点与槽位段是内置常量，不随配置变化。探测应答会写入已知主机清单，
  清单是「广播单向盲区」的反向补偿，按最近见过时间排序。
- **传输（TCP）**：发送方拨入接收方驿站，按需建立、可复用；帧同样是 NDJSON，超过
  1 MiB、非法 UTF-8、不可解析或非对象一律计数并关闭连接。
- **发送调度**：按「协作 × 对端」单元串行投递，FIFO 保序，ack 推进，超时重传。
- **接收管线**：按帧类型路由、准入、幂等去重、落盘、ack、钩子与投递回报；同一连接上的帧串行处理。

发现面按协议版本 `v:1` 与旧版互通；协作域另有硬能力闸门 `cap=2`：协作域帧根节点必须声明
`cap:2`，否则拒收。发现应答可携带 `participants` 能力（支持／不支持／未知），用于在建协作、
邀请或申请前判断对端是否支持会话级参与者。能力证据分级：只有直连单播探测是新鲜权威证据，
扫描、自介与转达缺字段只继承已有能力态。

## 3. 启动与自愈

### 3.1 核心启动序

核心按固定顺序启动；致命步骤失败以明确原因拒绝服务（尽力写入 `startupError`，否则只剩退出码），
LAN 端口被占用则降级服务而不是拒绝启动：

1. **取锁**：`run/core.json` 以独占创建（`wx`）取得。失败为 `EEXIST` 时进入仲裁循环；
   数据根不可写等其他 errno 直接拒绝。
2. **同根探测**：两道证据——端口道（目标端口双证据身份＋锚点段全段 probe-ack 身份）与
   数据面（`sessions/` 下本根新鲜旧形态会话文件）。任一命中即进入等待接管态并在此返回。
3. **自检**：数据目录、配置读取、日志目录、协作目录可写（真实落盘探针）。
4. **身份与配置落盘**：实例标识与配置补写先落盘后生效。
5. **LAN 栈启动**：端口被占用时进入降级服务（`ready` 照常、本地工具照常、LAN 工具返回明确降级文案），
   后台按 30 秒周期重试；占用者退场即自动恢复，无状态迁移。
6. **注册表加载**：协作目录加载与恢复（组件构造内含）。
7. **IPC 监听**：先监听命名管道／Unix 套接字，再监听 TCP 环回，成功后回填描述符。
8. **原子改写 `ready`**：进入就绪即开始宽限电平计时。

**取锁仲裁的确定性分支**（竞争失败者每轮重读描述符）：

- pid 已死 → 判陈旧，原子 rename 隔离锁文件；
- pid 活、状态为 `starting`／`waiting` 且心跳新鲜 → 等待（不删不抢；`starting` 另守启动截止期）；
- pid 活、状态 `ready` 且端点反证可连 → 已有核心在服务，本进程让位退出；
- 超出截止期或心跳超期 → 判死候选：连续两次独立观测（间隔不小于判死阈值，按单调钟计）+
  有界端点反证 + rename 前 token/startedAt 复校。端点不可连不单独构成陈旧判据；
  探测未完成同样不构成。

### 3.2 等待接管态

同根旧站点仍在运行时，新核心进入 `waiting`：不监听 IPC、不写 `ready`，**数据面零写**
（`collabs/`、`sessions/`、`known-hosts.json`、配置均不写），日志也不写（诊断只走 `statusDetail`），
仅 `run/` 豁免（心跳与凭据必需）。该状态每 30 秒重探测；退出有三条路径：

- 同根证据消失 → 重验锁仍为自己后，补做自检起的完整服务序并迁出；
- 寿命上界（60 分钟）→ 自行退出，后续桥到达会重新探测；
- `core stop --force` 显式终止。

`waystation core status` 会显示该状态并附处置指引：关闭同根旧版会话后自动接管。

### 3.3 桥的探测与四态判定

桥对核心的每一轮探测按写死的分类序处理：

| 观测 | 判定 | 动作 |
| --- | --- | --- |
| `core.json` 不存在或不可解析 | 陈旧 | 冷启（不可解析的锁由被冷启核心的仲裁清理，桥不删不抢） |
| 描述符有 `startupError` 且失败进程仍活、心跳新鲜 | 启动失败 | 按启动失败收口，不等截止期，也不冷启（防崩溃环反复 spawn） |
| 描述符有 `startupError` 但失败进程已死／心跳已停 | 陈旧（失败残留） | 允许重新冷启；真正 spawn 受「3 次/10 分钟」配额约束 |
| pid 死或非法 | 陈旧（崩溃残留） | 冷启（重生流的自愈入口） |
| pid 活但心跳停 | 僵尸 | 硬杀防护链；链全过才冷启，校验不过降级上报、不冷启 |
| `starting` 未超启动截止期，或 `waiting` 且 pid 活、心跳新鲜 | 启动中／等待接管 | 等待，不冷启、不偷锁 |
| 其余 | 可连接 | 连接尝试；失败按重连收口，不阻塞会话 |

其中核心侧的四个判定态是**陈旧、僵尸、启动中（`starting`）与等待接管（`waiting`）**；
「启动失败」与「可连接」是额外的收口分支。
每条 `ensureCore` 轮次至多 spawn 一次核心。冷启以 `detached`、`windowsHide`、stdio ignore 启动，
入口按模块位置相对解析，并显式剔除 `CLAUDE_CODE_*` 会话私有环境变量。首个工具调用的等待预算为
10 秒，连接与握手期限被预算钳制为硬期限。

### 3.4 硬杀防护链

对「进程活、事件循环卡死」的核心，硬杀只有一个入口，链序写死：

1. **判别器**：自动落链必须自有证据（描述符超期或心跳停）；显式授权（`--force` 等）或
   IPC 版本拒绝实证可放开证据要求，但慢启动窗口一律不越——排除慢启动误杀是第一要义。
2. **杀前复读**：重读 `core.json` 并与判定时的 pid/startedAt 对证，防杀继任者。
3. **杀后确认**：确认端点消失，才允许冷启。
4. **单次闸**：本进程对同一 pid 只真正发出一次终止信号；校验不过而未杀的不占额。
5. **校验不过**：不杀、降级上报（宁可不杀）。

返回结论为 `killed`、`endpoint-gone`、`verification-failed`、`not-eligible`、`already-once`。
残余风险（pid 复用、端点归属无法在进程面核验）在对应模块中有如实登记。

### 3.5 重生流与换代

**重生流。** 桥与核心连接断开后立即按上述分类序重探；快速重试上界为 3 次/10 分钟，
其后转 60 秒慢速重试，不形成风暴。桥侧常驻心跳（见 §2.1）在未注册态每拍调用 `ensureCore`，
因此慢速窗口不再是恢复上限；但真正的冷启 spawn 另有独立的 3 次/10 分钟配额，心跳不会退化成
spawn 风暴。重注册成功后触发核心侧恢复：席位重绑、暂存补投、挂起邀请补投、会话状态文件重建，
并输出一行 stderr 诊断（桥不写文件日志）。

**多桥并发冷启。** 核心被杀时同一数据根上的多个桥可能同时进入重生流：只允许一个核心赢得锁，
其余走仲裁。`core.json` 的原子替换对 Windows 并发读句柄造成的瞬时 `EPERM/EACCES/EBUSY` 做小步重试；
失败核收场时只在自己的锁仍被持有时写 `startupError`，不覆盖继任者的 `ready` 描述符。
两条合起来消除「并发冷启把成功核心写坏」的竞态。

**换代。** 版本权威是安装树（`package.json`），不是桥内存中的版本——否则「桥内存新、磁盘旧」
会形成无终止替换环。桥注册后比较「安装树目标版本」与「运行核心版本」：

- 目标高于运行 → 发 `replace` 请求，本桥成为 replacer；核心广播 `core-restarting` 后有序收尾退出；
- 目标不高于运行 → 直接服务（装回旧版不换代）；
- 握手被 `welcome{ok:false, code:'version'}` 拒绝 → 以拒绝帧携带的核心 `ipcV` 定方向：
  核心更高＝旧桥降级；核心更低＝直连替换（旧核不会主动退场，以版本拒绝实证走硬杀防护链）。

replacer 等旧核退场 10 秒，到期走硬杀防护链；硬杀后有 2 秒沉降期，端点消失才交付标准获取路径冷启
（避免与标准路径双 spawn）。非 replacer 桥进入「等待新核」态，30 秒截止；截止后交标准路径自愈。
换代轮次由桥侧台账截断：连续两轮未达目标即停止并降级上报。

### 3.6 空闲退场与常驻

- 缺省（`persistentCore` 为 false 或缺失）：末桥退场后核心在宽限期内退出（默认 60 秒，
  宽限内重开会话可秒级接上、无冷启）。
- `persistentCore: true`：核心常驻，无会话也在线；崩溃后无会话监督，对端视角静默离线，需要再开会话拉起。
- 存在本机活跃席位时，核心空闲退出不得早于 `max(核心空闲宽限, 席位宽限 + 10 秒)`，
  先完成离席广播／标记再退出。

## 4. 协作模式

模式在创建时定死，之后不可变。`managed`（协作）、`forum`（讨论）、`dispatch`（调度）三者的参与者、拓扑与持久化方式不同。

### 4.1 managed（协作）

- **拓扑**：站长（manager）＋成员（member）的星型。每个参与者是一个会话席位，站长本身也是席位。
- **台账**：权威台账在站长机，遵循单写者纪律——台账变更统一走「打补丁 → version 自增 →
  落盘 → 推快照」；`ledger.jsonl` 是追加写的状态快照流，加载取最后一条通过形态校验的完整行，
  成员机保存快照用于站长不可达时读取。
- **消息边**：成员的上行只能到站长所在机器，且定向只能落在站长席位；站长可发给任意成员席位，
  缺省发给除自己外的全部活跃席位。
- **状态**：`proposed`、`active`、`frozen`、`completed`、`terminated`。冻结／解冻／裁定、
  显式移交、窗口内接管与手动接管构成治理面；冻结期只允许读台账、裁定、退出与终止。
- **站长会话关闭、机器仍在线**：宽限到期后按 `joinSeq` 选可达最早成员自动移交；目标核按预授权
  自动接受、不要求目标机用户确认，以新站长名义签发，随后开 1 分钟接管窗口。
- **站长整机离线**：成员冻结（停写、非治理消息丢弃），**不自动选举**；必须由成员机用户确认后手动接管。
- **显式移交**：站长发起、目标会话确认（一次性令牌）、旧站长降级；不进入接管窗口，迟到 accept 拒绝。
- **任期分叉**：同 term 不同站长一律冻结上报；出口是终止本方分支并本地归档，不自动合并。

### 4.2 forum（讨论）

- **拓扑**：只追加的公共帖子列表；发起人是「第一个」，也是唯一能结束讨论的人。没有站长，
  也没有抢接／交接／冻结机制。
- **参与**：任何成员都可邀请；主动加入走「敲门」——广播 + 已知主机单播、少量重发，成员自动应答，
  随后任一成员本机放行，申请人在同意门确认后加入并回填历史。
- **发帖路由**：默认经中继（发起人）转达全体；中继本机发帖直接扇出；中继不可达时降级直投，
  后台恢复检测通过后回中继。中继侧按 `(作者, postId)` 去重后转达，重复副本不再二次注入会话。
- **收敛**：周期对表（默认 60 秒）拉取增量；同步游标只由拉取推进，尾部重叠窗口负责近端竞态，
  中段漏段由作者粒度摘要比对与有界回退重拉承担；成员关系以事件集并集收敛，join 未收敛前递增间隔重播。
- **容量**：活跃会话软顶 16（邀请侧约束，协议层名单硬顶 32）；并发场景允许暂时到 17。
- **消息面**：不设私聊，`to` 一律拒绝；帖子默认落本地列表，实时新帖进会话注入，
  回填／追赶帖只汇总一行并指引查看。

### 4.3 调度（dispatch，本机编排）

- **范围**：只在本机，不接入局域网。`mode:'dispatch'` 的邀请帧在协议层即被拒绝；
  伪造的调度帧在调度准入层拒绝并计数。
- **拓扑**：调度长 + 若干组员。角色只认启动期环境变量 `WAYSTATION_ROLE`——工具参数与聊天内容
  不能声明调度长；一个核心同时只允许一个调度（dispatch），不接受 `targets`。调度长心跳超时
  （默认 3 分钟无 ws 工具调用 / 无桥重连）后，另一个启动期 master 会话再次创建即**原地接管**：
  collabId、组员与任务表原样移交；旧调度长恢复后的调度操作返回 `dispatch-taken-over`。
- **收编**：调度长用 `ws_dispatch_scan` 扫描本机会话，`ws_dispatch_claim` 发起收编；
  交互式目标需用户确认（一次性令牌），无头／服务拉起的会话必须带 `WAYSTATION_ROLE=slave`
  才会被收编。确认门 `gate:'claim'` 关闭时收编请求自动绑定并注入知情通知。
  收编返回另带 `warnings` 资源提醒（空闲内存 / 组员数阈值，见 §1.5），只警告不拒绝。
- **会话标识**：`ws_dispatch_scan` 与 `ws_status` 的 dispatch 段为每个会话返回稳定短码
  `sessionCode`（`sessionId` 前 8 字符，与 `shortSessionId` 同源）；`name` 保留但标为提示——
  Claude Code 重命名 / 重启会让名字漂移。`ws_dispatch_claim` / `ws_dispatch_release` /
  `ws_send_message.toSessionIds` 接受 `sessionCode` 或完整 `sessionId`（精确匹配、不做前缀展开；
  零命中或歧义按「指定会话不在场」拒绝）。
- **autoClaim**：创建时开启后，创建即自动收编一轮，此后随核心节拍持续补收新出现的可绑定会话。
- **纪律包**：收编通知自动携带 `dispatch-rules.md` 全文；该文件是调度纪律的唯一权威源，
  通知发出时实时读取，改完即热生效。`ws_dispatch_rules_reload` 重读文件并向全体在编成员广播。
- **持久化**：编排状态默认持久化到 `<数据根>/dispatch/state.json`（`config.dispatch.persist=false`
  可退回纯内存，`config.dispatch.state_path` 可改位置）。文件只含可重建事实：collabId／名称／主题、
  调度长会话与最后心跳、组员列表、任务表（taskId → 状态／负责会话／最近 progress 摘要／
  acceptance／evidenceRef／时间戳；后两者是 v1 增量字段，schema 版本不升，旧文件缺字段按空处理）；
  不存消息流水、待确认收编申请、待补投队列等运行态。写盘只在关键节点（创建／收编／释放／
  任务状态变更／接管／待接管与恢复／结束），普通聊天不触发 IO；写失败告警一次并本进程内降级
  纯内存；损坏文件隔离为 `.corrupt-<ts>` 后按无状态启动。核心重启恢复时校验调度长是否在线：
  在线恢复 active，离线标记 `pending-takeover`；正常结束（`ws_end_collab`）删除状态文件。
  仍不进 `collabs/`（不建协作目录、不写 carrier／member／ledger／snapshot／outbox／inbox／invites／
  joins／seat／recovery／posts），消息历史与观察窗回放仍不保存。
- **保留期**：完成任务的保留时长 `retention.dispatch_hours`（默认 24h，0＝不保留完成项；未完成
  任务永不裁剪）；超过保留期的 `pending-takeover` 状态文件在启动时清理。组员/任务表容量有界
  （任务表上限 1000，满后拒绝新 taskId）。
- **消息**：复用 `ws_send_message`（可带 `toSessionIds` 与 `taskId`，类型限定 `task`／`progress`／
  `result`／`error`）与 `ws_end_collab`；投递唯一出口是本机注入路由，失败进有界待补投队列，
  桥重连后补投。
- **消息长度上限**：`config.dispatch.message_limits`（progress 默认 800／result 默认 3000／
  其他 text 默认 4000 字符，逐项 64–20000、非法回落默认）按最终投递正文计（report／evidence／
  acceptance 渲染后同样受限）；超限返回 `message-too-long` 并提示写文件、消息只发摘要 + 路径，
  不截断、不静默丢弃。其他模式不受影响（managed／forum 仍由协议层 4000 字符上限约束）。
- **结构化报告与完成证据**：`progress`／`result` 可选 `report`（summary／done／blockers／next；
  单项 ≤200 字符、数组 ≤20 项；带 report 时 `text` 可为空，正文由 report 渲染）；`result` 可选
  `evidence`（commit／tests／artifacts／gates，逐项校验、不强制）；`task` 可选 `acceptance`
  （1–20 项验收标准）。三者随帧投递（人可读渲染 + 帧 payload 原样字段），并写入任务表
  （lastProgress 摘要／evidenceRef／acceptance）。用错模式或类型明确拒绝（`report-not-allowed`／
  `evidence-not-allowed`／`acceptance-not-allowed`），不静默忽略。
- **任务超时提醒**：presence 节拍的 sweep 对 `assigned`／`active` 且最后任务消息距今 ≥
  `config.dispatch.task_stale_ms`（默认 30 分钟，范围 60 秒–24 小时）的任务，向调度长投一次
  `dispatch-task-stale`（taskId／负责会话／最后进度摘要）；`staleNotified` 只存内存，有新 progress
  时清位。只提醒，不改任务状态、不自动失败。
- **回执缺省值**：`config.dispatch.require_ack_default`（默认 false）为 true 时，调度长发出的
  `task` 未显式给 `requireAck` 按 true 处理；显式 false 仍可关闭。待确认账仍按既有 10 分钟超时收口。

### 4.4 模式对照

| 维度 | managed（协作） | forum（讨论） | dispatch（调度） |
| --- | --- | --- | --- |
| 范围 | 局域网 | 局域网 | 仅本机 |
| 拓扑 | 站长 + 成员（星型） | 平权＋发起人中继 | 调度长 + 组员 |
| 权威数据 | 站长机台账（单写者） | 各成员本地副本＋对表收敛 | 本机 `dispatch/state.json`（单写者） |
| 结束权 | 站长（含移交／接管） | 发起人 | 调度长（心跳超时可由新 master 接管） |
| 持久化 | 协作目录全套文件 | 协作目录全套文件（无 snapshot） | 编排状态单文件（消息历史不落盘） |
| 冻结／接管 | 有 | 无 | 无 |

## 5. 消息路由

### 5.1 出站队列

协作域的可靠投递使用每协作的发送队列 `outbox.jsonl`：

- 形态为追加写的状态快照流，加载时按 `msgId` 折叠（后写胜），并就地压缩，文件增长有界；
- 状态机：`queued`（未确认）→ `acked`（对方驿站已确认）→ `session`（对方核已完成会话投递阶段，终态）；
  `queued`／`acked` 超保留期 → `expired`（终态）；
- 按「协作 × 对端」单元串行投递（FIFO 保序），首投立即；未 ack 的重试恒定 10 秒，
  连续 3 次后转 60 秒低频，直至送达或过期；重试必重拨（应用层 ack 与超时是唯一判据）；
- 治理类帧（`freeze`／`unfreeze`／`decision`／`takeover-init`／`takeover`）与讨论的
  `end`／`join`／`leave` 豁免队列容量与过期——在未终态前永远可入队、不会被 TTL 回收；
- 普通消息的单协作待投配额默认 500 条；`delivery-status` 是「确认即终态」：收到 ack 直接收口，
  避免心跳回报在数小时内占满配额。

讨论的帖子走「在线直投 + 短重试」：首投 + 2 次重试、每次等待 1 秒，不落持久逐帖队列；
投递记录只在内存短期保留（10 分钟／512 条）。离线收敛由对方周期对表拉取兜底。

### 5.2 一站一帧与席位扇出

**出站按机器分组。** 一条逻辑消息发往 N 台机器＝N 个机器帧，逐机器生成 `msgId`；
同一台机器上的多个目标席位合成一帧，通过帧顶层的 `toSessions` 携带目标会话列表——
「按机器去重一帧」，不按席位拆帧。

**入站按席位扇出。** 接收核先校验 `toSessions`：出现即必须是 1–32 个合法会话标识的数组，
非法（非数组、空数组、坏元素、超长）**整帧拒绝**，绝不回落到全席广播。合法时只投列表内的本机席位；
未给出时，内容帧投本机活跃 `member` 席位，邀请帧例外（邀请是本机待办，受邀会话可能尚未成席，
可注入面包括桥注册目标与挂起邀请目标）。发送会话自己的席位不投。

坏目标只隔离丢弃并计数，不放大为「投给本机全部席位」。扇出逐席独立过静音栅栏、
独立记录结果（`injected`／`staged`／`duplicate`／`gated`／`dropped`）。

### 5.3 去重、ack 与暂存补投

- **幂等去重**：接收核按 `msgId` 在 `inbox.jsonl` 的投影集中去重；先落盘再 ack。
  重复帧重确认并按 inbox 中记录的扇出进度补投未完成席位；同 `msgId` 但类型或载荷不一致的重复帧
  拒绝补扇出并计数（仍保留 ack——链路确认与内容裁定是两件事）。
- **ack 语义**：「已到对方驿站」，不表示对方会话已读。准入拒绝或落盘失败不 ack，
  由发送侧按重试与过期收敛；协议没有 NACK。
- **本机暂存**：目标席位的桥不在线（或补投进行中）时，内容帧进入席位内存暂存；
  同 `sessionId` 在席位宽限内重连即按到达序补投。暂存默认上限为单席 100 条、单协作 500 条，
  超限丢最旧并计数；丢弃同时释放该 `msgId` 的去重记录，允许发送侧重投。
- **补投顺序**：桥注册回执（`welcome`）写出发送后，核心让出一拍再补投调度（dispatch）消息队列、
  席位暂存与挂起邀请——避免桥在握手完成前拒收 `push` 却已被记为「已送达」。补投期间席位保持
  `flushing`，新到的帧先入暂存队尾，保证不乱序。

### 5.4 投递语义边界

- **机器级终态**：对方核完成本机扇出后回一条机器级 `delivery-status`（`tier:'session'`）。
  它是「已处理到会话投递阶段」，不是远端逐席位终态，也不等于已读。
  仅暂存或零成功同样按终态回报（回报签发身份取原帧的 `from.sessionId`，不要求该席位仍活跃）。
- **本机逐席位明细**：本机侧另显示每个席位的实际结果（已注入／暂存待重连／判离席丢弃），
  可用 `ws_delivery_status` 查询；远端只显示机器级。
- **暂存的生命周期**：暂存只在核心存活期内有效。核心崩溃即丢失暂存，发送侧仍可能显示机器级已送达；
  这是机器级投递的已知边界。核心重启后，桥重连只能重绑席位，重启前核心内存中的暂存不会再补投。
- **离线语义**：「推停拉不停」——会话关闭或核心退场期间不再追发推送；重开会话后可经
  `ws_check_inbox`、`ws_view_ledger` 或观察窗补看。
- **`ws_send_message` 的 `delivery` 增量字段**：逐目标给出 `delivered`（已投进目标会话）、
  `queued`（暂存待补投，附 `queuedUntil`）或 `failed`（附原因），顶层 `state` 归并为
  `delivered`／`queued`／`failed`／`partial`。协作模式的本机旁路按逐席位注入结果映射；远端机器
  只能确认「已受理入队」，一律如实报 `queued`，不把机器级受理谎报成会话已投递。
- **调度（dispatch）会话级确认**：`requireAck` 只允许调度长发出的 `task`；未显式给值时按
  `config.dispatch.require_ack_default`（默认 false）处理。投递文本附回执指引
  （含本条 `msgId`）；目标会话用 `ws_send_message { ackFor }` 回执后，核心向调度长另行投递
  `dispatch-ack` 通知。发送结果在 `delivery.ack = { required, state: 'pending', pending }` 列出
  待确认 `msgId`；待确认条目默认
  10 分钟超时，超时、目标离席或补投队列溢出都会向调度长回报 `dispatch-ack-timeout`，不静默挂起。
  调度消息的暂存队列带宽限截止（默认与席位宽限同源），presence 节拍重试，超期丢弃并回报。

### 5.5 静音与注入栅栏

静音是**席位级、纯本机**开关：只影响实时内容是否注入本会话，不广播、对端无感，也不影响落盘与观察窗。
静音期内容帧在扇出时被逐席抑制，治理／邀请／离席／结束等帧豁免。
被抑制的帧不进本会话，但机器级投递确认照旧；实时内容仍可在事后经查看器、`ws_view_ledger` 或
`ws_check_inbox` 补看。

讨论侧另有三类注入分流：拉取两件套（`history-request`／`history-bundle`）从不注入会话；
帖按 `(作者, postId)` 去重命中时抑制再次注入；讨论侧被忽略的冻结族帧同样不注入。
这些声明只在对应通道内被采信，不泛化到 managed。

## 6. 席位与恢复

### 6.1 席位文件

每个协作目录下的 `seats/<sessionId>.json` 是本机会话席位的持久面，字段包括：

| 字段 | 含义 |
| --- | --- |
| `sessionId` | 完整会话标识（也是文件名） |
| `version` | 席位文件形态版本 |
| `role` | `manager`／`member` |
| `state` | `joining`（两段式入席中）／`member` |
| `joinSeq` | 入席序号（站长自动移交按它选最早可达成员） |
| `joinedAt` | 入席时刻 |
| `muted` | 本席位静音开关 |
| `unverified` | 两段式入席中尚未收到含本席快照的标记 |

桥绑定、暂存队列、席位收件箱与去重集属于核内运行态，不写入席位文件。
`carrier.json` 是新协作目录的第一份落盘文件，描述目录形态与协作身份；先写 carrier 再写台账，
两步之间崩溃的目录写 `recovery.json` 标记并按只读处理，不重建空台账。旧形态目录写
`migration.json` 标记为 legacy，只读保留。

### 6.2 两段式入席

managed 的加入链路为：**申请 → 站长待批准 → 本会话确认 → 站长写入名单**。

- 申请与批准都按会话记账；同会话对同协作未决期内重复申请幂等，新窗口＝新申请；
- 批准后申请人处于 `joining`，收到含本席的快照后才转为正式 `member`；期间可收注入、禁发消息；
- 待批准上限为每协作 16 条；申请时限默认 24 小时，两段式确认时限默认 60 秒；
- 未在席的会话发送会被拒绝并指引先受邀或 `ws_join`；0.2.0 无写类调用夺席。

forum 的直接加入没有批准门：本会话已在席时 `ws_join` 立即生效；未在席时封装完整的敲门流程。

### 6.3 核心重启后的宽限重绑与对账

**正常退出标记。** 核心有序退出前：

1. 对未送达的 `leave` 做有界冲刷（最多 5 秒或直到 ack），
2. 把本机席位快照写进 `run/core-stop.json`（`{ at, seats, pendingLeave }`），
3. 再停心跳、关协作／网络／IPC，最后对证删除 `run/core.json`。

**重启对账。** 新核心启动时读 `core-stop.json`：标记内席位在宽限期（默认等于
`sessionSeatGraceMs`，60 秒）内重新绑定桥的，视为未离席；未重绑的，交回既有离席路径——
成员核发 `leave`、站长核移除名单行——完成后把标记回写为 `pendingLeave:false`（标记保留不删，供审计）。
宽限起点从本核恢复时刻起算；桥注册本身就是「已重绑」证据，重绑后又断开也属已重绑，
其后的离席由常规宽限接管。

**桥重注册的恢复动作。** 桥注册后核心：

1. 绑定该会话在本机各协作的席位到新桥，撤销过期的确认门状态；
2. 让出一拍（覆盖握手回执在途）；
3. 补投调度（dispatch）消息队列、席位暂存、挂起邀请与确认门通知；
4. 桥在注册成功后补发一次最新会话元数据（`register-update`），核心据此刷新会话状态文件。

**席位宽限。** 桥断开时席位不立即消失，核心记下关闭时刻；同 `sessionId` 在宽限内重连即取消离席，
席位的暂存保留并补投。宽限到期才离席：暂存丢弃并计数，席位文件删除，协作层广播相应离席事实。
站长席位关闭走自动移交路径；普通席位关闭走常规离席路径。

## 8. 已知限制

- **无自动故障转移（managed）**：站长整机离线时协作冻结，必须由成员机用户确认后手动接管，
  不自动选举、不自动宣告。自动移交只在「站长会话关闭、机器仍在线」时发生；目标已接受但签发帧丢失
  会停在只读等待，需要人工处置。同 term 不同站长一律冻结上报，不自动选胜者。
- **投递保证是机器级**：一条逻辑消息按机器拆帧，接收核按 `toSessions` 扇出到本机席位；
  不提供远端逐席位终态。同机某席位离线时，暂存只在核心存活期内有效，核心崩溃即丢失；
  发送侧仍可能显示机器级已送达。暂存有容量上限，超限丢最旧并计数。
- **调度（dispatch）持久化边界**：编排状态（组员 / 任务表 / 调度长心跳）默认持久化并可恢复；
  消息流水、台账、收件历史与观察窗回放仍不保存（`ws_view_ledger`／`ws_check_inbox` 对调度明确回
  「不保存历史」）。`config.dispatch.persist=false` 时为纯内存（核心重启即丢）；持久化写失败时
  自动降级纯内存（不阻塞编排）；损坏状态文件隔离后按无状态启动。`requireAck` 的待确认账
  （`pendingAcks`）与补投队列截止（`queueDeadlines`）仍是内存态，核心重启即丢失，不写入
  `dispatch/state.json`（已知集成缺口，留待后续版本）。
- **forum 的中继枢纽**：中继（发起人）是全部帖子的必经转达点，可静默延迟或丢弃转达；
  常见情形由落后方周期对表拉取兜底，但中继本身是新的可用性面。发起人退出后讨论不再有人能结束它。
- **发现面的边界**：发现依赖探测应答、启动自介与已知主机清单；从未与本站点接触过、又不在扫描段内的
  同机实例扫不到（不做地址枚举）。默认扫描段为 7321–7328。
- **在线 ≠ 有会话**：宽限期的尾巴与 `persistentCore` 常驻态都会让对端扫到「在线但无会话」的机器；
  「已投进对方会话」也不等于已读。
- **IPC 信任边界**：本机同用户进程可读 `run/core.json` 的 token 并连接核心、驱动工具面
  （含同意门／裁定类）；不构成对同用户恶意进程的防护。对端进程身份校验在 Node 面不可得，
  实现按「接受＋如实登记」处理。
- **协作域版本硬断裂**：0.1.x 与 0.2.0 的协作域不互操作；旧版对端在发现面仍可见，
  但邀请／申请／建协作被能力闸门拒绝，旧协作只读。
- **观察窗是只读面**：本地 Web 观察窗只绑定回环、只读零写盘，不替代协作数据面；
  终端讨论查看器与它是同一观测面的两种形态。
