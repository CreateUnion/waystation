## 1. 协作域帧能力根 `cap:2`

**契约名**：协作域帧能力闸门（0.2.0 硬断裂）

**内容**

- 除 `ping` / `pong` / `ack`（`TRANSPORT_TYPES`）外，所有协作域帧的根节点必须 `cap === COLLAB_CAPABILITY`（=2）；
  缺失或不等于 2 一律拒收，错误文案为「对端版本不支持会话级协作（需 0.2.0+）」。
- `PROTOCOL_VERSION` 保持 1；发现面仍按 `v:1` 与 0.1.x 互通。断裂只由 `cap` 显式声明，不靠版本号。
- 出站统一经 `withCollabCapability(frame)` 叠加 `cap`，不得手写或漏写（防「自家预检拒自家帧」）。
- `MESSAGE_TYPES` 新增 `seat-presence`、`join-confirm`；协作域帧 `from.sessionId` 必填（transport 的
  `ping`/`pong`/`ack` 豁免；签发席位规则见设计 §7.1，`seat-presence` / `delivery-status` 的专项语义见 §5）。
- 旧对端仍在发现面可见（可扫描、可 ping），但邀请 / 申请 / 建协作 / 消息等协作操作被能力闸门明确拒绝；
  0.2.0 双端必须同版。

**为什么不可破坏**

- 这是区分「旧版节点」与「会话级节点」的唯一线级开关。旧版没有席位、任期、两段式入席语义；放行无 `cap` 的帧，
  会把 `managerTerm`/`joinSeq`/`sessionId` 等会话级字段交给旧逻辑解释，造成名单与任期分叉，且事后无法可靠识别。
- 发现互通与协作断裂必须解耦：提升 `PROTOCOL_VERSION` 会连发现面一起断，失去「旧对端可见但不可协作」的能力。

**可检测签名**

- `src/net/protocol.js:53` `COLLAB_CAPABILITY = 2`
- `src/net/protocol.js:57` `withCollabCapability`
- `src/net/protocol.js:104` 非 transport 帧校验 `frame.cap !== COLLAB_CAPABILITY`
- `src/net/protocol.js:39-48` `MESSAGE_TYPES`（含 `seat-presence` / `join-confirm`）
- `src/net/protocol.js:8` `PROTOCOL_VERSION = 1`；`src/net/protocol.js:74` `TRANSPORT_TYPES`
- 测试：`test/net-protocol.test.js`（grep `COLLAB_CAPABILITY`）

**变更流程（停点）**

- 属接口契约变更（停点）：停写回报用户 → 用户批准 → 设计 §7 与契约同提交更新 → 校验器/测试/README 同步 →
  双端同版真机验证。
- 放宽兼容（如允许 `cap:1`）属语义裁定，必须由用户拍板并写定文档；不得在实现里默认降级。

## 2. 发现面 `participants:2` 与 known-hosts v4

**契约名**：会话级参与者能力字段与三态判定

**内容**

- 加法字段 `participants:2` 出现在 `probe-ack`、`join-knock`、`join-ack`、`join-resolve-ack`；旧对端忽略该字段。
  探测请求本身不声明能力（`probe` 不带 `participants`：这是「没有情报」，不是「不支持」）。
- 三态语义（`participantsStateOf`）：`2` = 支持；`0` = 对端应答存在但缺字段（旧版）；字段缺席 = 未知（从未观测到）。
  `ws_list_hosts` 按此展示「支持 / 不支持 / 未知」。
- 证据分级（2026-10-21 语义裁定）：
  - 显式 `participants:2` 恒升级（任何来源）；
  - **直连单播 `probe-ack`** 缺字段是新鲜权威证据，可把已知「支持」降级为「不支持」（2→0），并记录
    `source:'probe'` 与 `checkedAt`；
  - 扫描、自介、转达帧缺字段只**继承**已知值，不降级；无响应 = 未知；
  - 探测结果必须先写入 `known-hosts` 再返回，保证探测结论与 `ws_list_hosts` 清单同源；目标按 `instanceId` 关联，
    应答 `instanceId` 不符 → 未知，不得按来源地址归户；超时重试一次后仍无应答才判未知。
- `known-hosts.json` 存储版本升 4：条目可含 `participants`（2/0）、`source`（`probe`/`scan`）、`checkedAt`；
  旧条目缺字段按未知读取，下一次写入即 v4 形态。未知与「不支持」是两个语义，不混同。
- 能力闸门落在服务层：邀请 / 申请 / 建协作前要求目标能力为「支持」；未知先扫描或单播探测；不支持明确拒绝
  （旧节点不支持会话级席位）。

**为什么不可破坏**

- 该字段决定对端是否具备会话级席位语义。把「未知」当「不支持」会误拒可用对端；把旧版当「支持」会让两段式入席、
  `seat-presence`、`sessionId` 路由在对端无声退化或悬挂。
- `known-hosts` 的 `participants/source/checkedAt` 是跨重启的能力证据；格式或降级规则改变会导致
  「探测说不支持、清单仍说支持」的分叉，直接误导邀请/加入闸门。
- 加法字段是发现面与 0.1.x 保持互通的边界：旧对端忽略它，新对端靠它识别断裂。

**可检测签名**

- `src/net/protocol.js:163` `PARTICIPANTS_CAPABILITY = 2`；`:165` `isParticipantsCapability`；`:170` `supportsParticipants`；
  `:175` `withParticipantsCapability`
- `src/net/discovery.js:978` `buildProbeAck`（带 `participants:2`）；`:507` `sendJoinAck`；`:1085` `sendKnocks`；`:693` `buildJoinResolveAck`
- `src/net/discovery.js:365` `observedParticipantsOf`（缺字段=0）；`:847` `probeCapability`；`:907` `rememberProbeEvidence`
- `src/net/known-hosts.js:40` `STORAGE_VERSION = 4`；`:17-18` `PARTICIPANTS_SOURCE_PROBE` / `PARTICIPANTS_SOURCE_SCAN`；
  `:26` `participantsStateOf`；`:212` `mergeOptionalFields`；`:241` `participantsEvidenceOf`；`:255` `inheritedParticipantsOf`；
  `:272` `applyProbeEvidence`；`:303` 落盘 `{version: STORAGE_VERSION, hosts}`
- `src/tools/hosts.js:33` `participants: participantsStateOf(host)`
- 测试：`test/net-discovery.test.js`、`test/net-known-hosts.test.js`

**变更流程（停点）**

- 字段语义、三态口径或证据分级变更属接口契约/语义裁定（停点）：用户拍板 → 设计 §7.2 与本清单同提交 →
  探测/存储/展示三层测试同步。
- 若未来升 `participants:3`：必须保留对 `2` 的读取与判定，不得让 0.2.0 节点被误判「不支持」；迁移不得删除存量
  `known-hosts` 条目。

## 3. 协作目录形态标记与写门（`carrier.json` / `recovery.json` / `migration.json`）

**契约名**：协作目录的形态标记、半写恢复与只读写门

**内容**

- 新协作的第一份落盘文件是 `carrier.json`，`format` 取值 `session-seats` 或 `invite-stub`
  （`CARRIER_FORMATS`）；`version:1`（`CARRIER_VERSION`）。字段：
  `{format,version,collabId,name,topic,mode,endpoints,manager?:{instanceId,sessionId,identityName,term},originator?,forumMeta?,syncCursor?,snapshotVersion,createdAt}`；
  冻结态可另携 `freezeReason`（只读展示用）。读到更高 `version` 按不可用处理（fail-safe，不静默降级重写）。
- `session-seats` = 会话级新协作，必须有台账；`invite-stub` = 仅有挂起邀请、无台账，`snapshotVersion` 必须为 0，
  不判损坏、不判半写；首次真正入席时替换为 `session-seats`；邀请 TTL 到期后保留 stub、只清邀请记录。
- 半写：`carrier.json` 已写、台账未写 → 写 `recovery.json {state:'half-created',at,reason}`，目录按**只读**处理，
  **不重建空台账**（非终态空台账不合法）。创建路径固定 carrier → ledger，两步之间不得调用写门。
- 旧形态协作（存在旧 `member.json`，且无新 `format` 标记、无 `migration.json` / `recovery.json`）启动时写
  `migration.json {legacy:true,archivedAt,reason}` 归档为只读；不改写旧台账。
- `classifyCollabDir(dir)` 的目录分类：`missing | empty | session-seats | invite-stub | legacy | archived-legacy | recovery | corrupt`。
  无标记且无 `member.json` / `pending-invites.json` 的非空目录判 `corrupt`，不自动按 legacy 处理。
- 写门单一入口 `assertWritable(collabDir)`：所有写类工具与入站写（`persistInbound`、`pending-invites.json`、
  `handover-offers.json`、`inbox.jsonl` 等）统一经过；`legacy` / `archived-legacy` / `recovery` / `corrupt` 一律拒绝
  （`reason:'legacy'|'recovery'|'corrupt'`）。内存标记与文件标记同时检查；标记写失败时继续按只读处理（失败安全）。

**为什么不可破坏**

- 形态标记是「新会话级协作 / 仅挂起邀请 / 旧版协作 / 半写目录 / 损坏目录」的唯一判据。判错会二选一地造成不可逆后果：
  把半写目录当空协作写入空台账（非法台账、破坏恢复证据），或把旧版目录当新协作改写（丢用户数据、破坏回滚）。
- 写门是只读承诺的机器执行点；任一写路径绕过它，legacy / recovery 目录就会被静默改写，重启后的恢复与审计依据消失。
- `carrier.json` 是用户数据的一部分，字段语义变化会影响 0.1.x 档案识别与观察窗只读展示。

**可检测签名**

- `src/collab/carrier.js:18-20` `CARRIER_FORMAT_SESSION_SEATS` / `CARRIER_FORMAT_INVITE_STUB` / `CARRIER_FORMATS`；
  `:23` `CARRIER_VERSION = 1`；`:36` `isCarrierShape`；`:60` `isCarrierVersionShape`；`:141` `readCarrier`；`:156` `readCarrierFormat`；`:165` `writeCarrier`

## 4. `joins.json` v2 两段式入席持久化

**契约名**：`joins.json` v2 形态、写点纪律与 v1 只读兼容

**内容**

- 路径：`<collab>/joins.json`（`joinsFilePath`），站长机维护。0.2.0 写侧形态唯一：
  `{v:2,pendingJoins:[{joinId,instanceId,sessionId,managerTerm,grantVersion,requestedAt,expiresAt}]}`。
- `pendingJoins` 是「已发 grant、待 `join-confirm`」的唯一写盘投影；`confirmed` 不落盘，出现 `confirmed:true` 即拒收。
  已确认席位以**共享名单/台账**为准，不得从本文件恢复。
- 写点纪律：只在 begin/refresh、abort/expire/invalidate、unconfirm 之后，以及名单提交成功之后写；
  `confirmJoining` 成功与名单提交之间**禁止写盘**（否则崩溃恢复会丢 grant 或复活已确认席位）；启动 restore 后必须与共享名单对账。
- 读取面对 v1 兼容：`{v:1,pendingJoins,approvals}` 可读，只取 `pendingJoins`，`approvals` 退役、新代码忽略；
  v1 旧待批准行缺 `joinId`/`managerTerm`，逐条拒收并计数，不整档判坏。
- 整档损坏 → 备份 `.corrupt-<ts>`、告警计数、按空态继续；**不得静默清零后覆盖**。单条损坏只丢该条并计数。
- `approvals` 段退出舞台：旧文件留盘不删（删除属停点），不以 approvals 作为新入席的获准权威。

**为什么不可破坏**

- 两段式入席依赖「grant 已发出、等待确认」这一跨重启状态；格式或写点改变会在崩溃窗口丢 grant（申请人永远 confirm 不了），
  或把已确认记录重新写回 `pendingJoins`（复活席位、绕过容量）。
- `approvals` 与共享名单是两套成员权威；保留 approvals 写入会制造「本地认为在席、共享名单没有」的分叉。
- v1 只读兼容是回滚/降级期的安全网；写侧仍产出 v1 会破坏 v2 的单一权威。

**可检测签名**

- `src/collab/joins.js:432` `JOINS_FILE_VERSION = 2`；`:580` `saveJoiningFile` 写 `{v: JOINS_FILE_VERSION, pendingJoins}`
- `src/collab/joins.js:49` `isJoinsShape`（v1/v2 读侧兼容）；`:60` `isJoiningRecordShape`（拒绝 `confirmed`）；`:567` `loadJoiningFile`
- `src/paths.js:67` `JOINS_FILE_NAME`；`:71` `joinsFilePath`
- 测试：`test/collab-joins.test.js`
- 设计 §4.4 / §6.2 的 `joins.json` 行；契约 M4「joins.json 写点」

**变更流程（停点）**

- 持久化格式变更（v2 → v3 或字段增删）属停点：用户批准 → 迁移/兼容读取器（至少能读 v2）→ 设计 §6.2 与本清单同提交 →

## 5. 席位心跳 `seat-presence` 与机器级 `delivery-status`

**契约名**：席位 presence 载荷与投递回报的机器级语义

**内容**

- `seat-presence` 载荷：
  `{collabId,instanceId,sessions:[sessionId...],sentAt}`；`sessions` 为**完整 sessionId**（非短码），1–`MAX_ACTIVE_SEATS`（32）项、
  不得重复；载荷 `collabId` / `instanceId` 必须与帧的 `collabId` / `from.instanceId` 一致。
- 签发席位：managed 站长机固定以站长席位签发，成员机以本机在该协作的活跃席位签发（多席取码位序最小者）；
  forum 以中继席位签发；本机零活跃席位时不发。帧 `from.sessionId` 必填。
- 刷新纪律：列表级刷新——只刷新 `sessions` 数组内的席位；同机未列出的旧席位标记「本机未列」，连续超时判离席。
  只信直连（传输对端实例 = `from.instanceId`，且无 `originMsgId`）；forum 仅放行「本机记录的当前中继」转发的 `seat-presence`。
  presence 只用于离席与可达性，**不用于选举或推导继任者**。
- `delivery-status` 载荷保持 `{refMsgId, tier:'session'}`，不加 `sessionId`；`ack` 同样不加。
- 投递记账为**机器级**：一条逻辑消息向 N 台机器发送 = N 个机器帧、逐机器 `msgId`；`ws_delivery_status` 展示机器级状态
  加本机席位明细。`from.sessionId` 取首个成功注入/暂存的本机席位；零成功时仍携原消息出站条目记录的 `from.sessionId`
  （历史发件身份，不要求该席位仍活跃）；**不得生成无 `from.sessionId` 的 cap=2 帧**（对端协议层会拒收，发送侧只能等 TTL）。

**为什么不可破坏**

- presence 是离席判定、自动移交与「目标是否可达」的输入；若携带短码，跨节点匹配会歧义或前缀碰撞；若机器级心跳无差别刷新
  全部席位，会掩盖离席并阻止自动移交；若把 presence 用于推导 manager，会绕过 §2A 受理表并产生同 term 分叉。

## 7. 共享台账 `ledger.jsonl` / `snapshot.json` 持久化语义

**契约名**：共享台账的任期、序号、窗口与终态形态

**内容**

- `ledger.jsonl` 是追加写的完整台账流：每行一次变更后的完整台账；加载取**最后一条通过形态校验的完整行**
  （`loadLedger`）。`snapshot.json` 为整体替换写，含 `version/digest/receivedAt/from/ledger`。
- 台账字段：`managerTerm`（初始 1，每次站长变更 +1，上限 `MAX_MANAGER_TERM = 2^31−1`，到顶拒绝变更、不回绕）、
  `joinSeqNext`（managed 正整数，初始 2）、`manager:{instanceId,sessionId,identityName,term}|null`、
  `managerWindow?:{windowBaseTerm,windowEndsAt}`、`version`（每次台账变更 +1）、`members`、`status`、`board`、`createdAt`、`updatedAt`。
- 名单行：`{instanceId,sessionId,identityName,role,state:'member',joinSeq,joinedAt}`；唯一性键 `(instanceId,sessionId)`；
  managed 的 `joinSeq` 单调不减（相等允许、严格递减算损坏，按 `(joinSeq,sessionId)` 破平）。
- 非终态 managed 名单有且仅有一个 `role:'manager'`，且与 `manager` 席位逐字段一致；`manager.term === managerTerm`。
- `managerWindow`：仅非终态；`windowBaseTerm === managerTerm`；终态必须清除。窗口只在 `via='auto'` 变更时开启。
- 终态 `status ∈ {completed,terminated}` 允许 `members:[]`、`manager:null`；`managerTerm` 保留最后值；`version` 仍递增。
- 一次站长变更 = 一次原子台账变更（旧站长移除/降级、新站长提升、`managerTerm`/`version`/`digest` 同一次落账）；
  `digest` 为覆盖最终台账的 SHA-256（64 位小写十六进制，`DIGEST_PATTERN`）。
- 快照受理/排序按 `(managerTerm, version)`（`compareSnapshot`）：term 高者优先；同 term 不同 manager = 冲突（不比较 version，
  不静默合并）；同 term/manager/version = 幂等。

**为什么不可破坏**

- `managerTerm`/`version`/`manager` 是所有节点判定「谁有权写、哪份快照更新」的唯一依据；形态或单调性改变会让受理表
  A1–A14 失效，出现双站长、term 回退或快照互拒。
- `digest` 覆盖最终台账，是快照/变更完整性校验的锚；改字段顺序或计算口径会让所有旧 digest 失配，节点永久无法收敛。
- 终态 `manager:null`/空名单是归档的合法形态；若沿用非终态校验（站长唯一/名单≥1），已结束协作将无法加载或会被误判损坏。
- 台账是用户数据与审计证据；追加流与最后合法行加载是崩溃恢复的基础，不能被「整体重写」替代。

**可检测签名**

- `src/collab/model.js` `isLedgerShape`；`isLedgerRosterShape`；`isManagedLedgerShape`；`managerRowMatches`；
  `isManagerWindowShape`；`compareSnapshot`；`isLedgerHeadShape`
- `src/collab/store.js:9` `LEDGER_FILE_NAME`；`:26` `ledgerDigest`；`:44` `loadLedger`
- `src/net/protocol.js:515` `MAX_ACTIVE_SEATS = 32`；`:519` `MAX_MANAGER_TERM = 2147483647`；`:523` `DIGEST_PATTERN`
- `src/net/protocol.js:566-567` 帧规则表（`join-confirm` / `seat-presence`）；`manager-changed` / `handshake` / `snapshot` 字段

## 8. 数据目录、端口锚点与本地文件格式
